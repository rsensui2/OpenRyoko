# OpenRyokoの設定

ユーザーの「こう動いてほしい」を、稼働しているOpenRyokoの設定と検証結果に落とし込む。説明の依頼なら説明まで、変更の依頼なら必要な変更と反映確認まで進める。設定を依頼されたことを、公開・配信・認証解除や別インスタンス変更の許可に拡張しない。

## まず対象と対応機能を確認する

1. 対象のインスタンス名、実行ホスト／コンテナ、設定ホーム、gateway接続先、起動方法を確認する。設定ホームと作業ディレクトリは別物。`~/.ryoko` やポート7777を決め打ちしない。
2. 依頼に関係する設定とAPIの状態を読む。`ryoko api` は選択インスタンスの認証を扱う。カスタムホームなら `RYOKO_HOME`、名前付きなら `ryoko -i <name>` を全コマンドで一貫させる。ホスト側とコンテナ内の同名パス・CLI・認証は同一とは限らない。
3. CLIの `--version`、起動中プロセスの実体／イメージ、該当パッケージの実装を照合する。`config.yaml` の `jinn.version` はマイグレーションの記録であり、稼働コードの証明ではない。
4. 下の参照資料から今回必要なものだけ読む。稼働パッケージの `src/`、またはnpm同梱の `dist/src/`（`.js` / `.d.ts`）を根拠にする。型、サンプル、UIにキーがあるだけでは実装済みと判断しない。呼び出し元まで追う。

| 依頼 | 読む資料 |
|---|---|
| 機能を知りたい、接続・人格・モデル・運用を設定したい | [設定と反映方法](references/platform.md) |
| Claude Code／Codexの利用制限・無応答・タイムアウト・切り戻し | [実行エンジンとフォールバック](references/engine-fallback.md) |
| Slackで空気を読む、Jevを有効化、判定用CLIを減らす | [JevとSlackの応答判定](references/jev.md) |

開発中機能には対応済みの稼働実装が必要。未対応なら有効にならないキーを書いて成功扱いしない。利用可能な代替と、必要な更新・反映作業を具体化する。設定依頼だけで開発ブランチのマージやパッケージ公開まで行わない。

## 変更と検証

- 希望する動作、変更するキー、影響範囲、再起動の要否を短く示す。対象や選択が会話から確定していれば、同じ許可を聞き直さない。不足が結果を左右するときだけ確認する。
- 既存設定を読み、変更対象だけの差分を作る。gateway稼働中は原則 `PUT /api/config` の部分更新を使う。配列は全置換なので、`connectors.instances` やモデル一覧は既存要素を保持する。`GET /api/config` のマスク値 `***` をファイルへ保存しない。
- 直接編集が必要なら、対象ファイルを所有者だけが読める場所にバックアップし、最新内容との差分を確認して、YAML/JSONを検証してから同じディレクトリ内でatomic writeする。無関係な設定・秘密・コメントを不用意に置換しない。
- API成功は保存の確認にすぎない。設定の再読込、reloadログ、コネクタのhealth、対象経路の動作を確認する。CLIインストールとログイン／モデル利用権限も別々に確認する。
- 再起動が必要なら起動方法に合わせる。自分を実行中のgatewayを停止すると確認できなくなるため、外側の管理プロセスで反映・確認する手段を整える。無関係なインスタンスを止めない。
- 不具合時は今回の差分を戻し、再度反映を確認する。変更後に他者が編集した設定を古いバックアップで丸ごと上書きしない。

報告には対象、変更した設定、反映・検証結果、残る制約を含める。秘密値や会話本文を報告・共有スキルに転記しない。故障修復は同梱 `self-heal`、社員の作成・役割変更は `management`、定期ジョブは `cron-manager`、バージョン移行は `migrate` の該当手順も参照する。
