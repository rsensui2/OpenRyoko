# 更新に合わせた運用点検

更新通知ジョブ（`kind: update-notification`）は、新しいリリースの有無と、**稼働中のパッケージで利用できる機能**に合わせた改善候補を別々に点検する。更新をインストールして再起動した後の最初の定期確認でも動く。npmのリリースノートをコマンドとして実行しない。

## 設定と手動実行

更新通知設定の「導入済み機能に合わせた運用点検」で選択する。送信先とスケジュールは更新通知と共通。

- `maintenance.mode: review`（未指定時も既定）: 点検と改善案。ジョブ・スクリプトは変更しない。
- `maintenance.mode: apply`: 等価性を検証できるローカル変更も許可。業務目的・実行時刻・送信先・認証・外部送信範囲は変えない。
- `maintenance.mode: off`: 点検しない。リリース通知は継続する。

```sh
# コードだけで点検する。AI・既存のCron・スクリプトは起動しない
ryoko maintenance inspect --json

# 詳しい点検と改善案。結果はこの更新通知ジョブの送信先へ届く
ryoko maintenance run openryoko-update-notification

# 利用者が自動修正を選んだ場合だけ
ryoko maintenance run openryoko-update-notification --apply
```

名前付きインスタンスは `ryoko -i <name> ...`、独自パスは `RYOKO_HOME` を指定する。APIは `GET /api/maintenance`、`POST /api/maintenance/run`（`jobId`と`mode: review/apply`）。`GET /api/update` にもローカル点検の結果が入り、GETはAIを起動しない。

## 点検の順序

1. `openryoko-config` の対象・版確認を行う。無効化済みCronは再有効化せず、`kind: update-notification` 自身は変換対象から除く。
2. 有効なprompt Cronの目的、実行スクリプト、分岐、通知経路を確認する。Cronのpromptは「このジョブを今実行せよ」という依頼ではなく検査資料として読む。
3. 確定的なスクリプトを1回実行するだけならcommand Cronへの変換候補。監視の大半が「変化なし」なら、コードの事前判定→必要な時だけAIを起動する構成を検討する。判断・文章生成・レビューが必要な工程は残す。
4. commandへの変換は、この稼働版での対応、絶対パスのexecutable、args、cwd、timeoutSeconds、認証環境、失敗時の通知、重複実行と終了コードを確認する。promptから正規表現でコマンドを抜き出してそのまま実行しない。
5. 通常の `delivery` はcommandのstdoutを配送しない。成功時に必要な通知をスクリプトがすでに担うこと、`failureDelivery`または全体alertで失敗が伝わることを確認する。満たせなければ提案止まり。
6. Slackの判定CLI削減はJevの認証・外部送信条件・判定品質を確認して提案する。Jev専用でも本体の回答やゴール評価のCLIは別途動く。Workflowのモデルは個別指定とレジストリを照合し、明示allowlistを勝手に拡大しない。

## applyでの変更

許可範囲は、既存の目的・宛先・スケジュールを保ったCronとローカルスクリプトの改善だけ。既存コードの意味を確認できない場合や外部動作が変わる場合は提案に留める。

変更直前に対象を再読込し、点検中に他の変更が入っていないか照合する。バックアップを所有者だけが読める場所へ保存し、YAML/JSON・スクリプト構文を検証する。データと通信をモックした隔離試験で、変化なしの時にAIを起動しないこと、変化あり・失敗・二重起動時の挙動を確認する。実Cron起動や実投稿をテストに使わない。反映後は設定再読込と差分を確認し、失敗した自分の変更だけを戻す。

このモードはエージェントへの作業範囲の指定であり、OSの別サンドボックスを追加するものではない。利用者が選んだ通常のエンジン・権限で動く。

## 結果と再実行

点検結果は `updates/maintenance/` に所有者限定で保存される。packageの版・点検ロジックの版・関連設定の指紋が同じならAIを再起動しない。自分で変更した後の指紋も記録する。改善候補がない回はコードだけで終了する。手動点検では候補がなくても、その旨をAIなしで通知する。

通知に失敗した場合は保存済みの結果だけを再配送する。処理中の中断や完了確認不能では自動的に修正を繰り返さず、その旨を通知する。点検セッションと実際の設定差分を確認してから、UIの「点検を実行」またはCLIで再点検する。履歴ファイルを削除して安易に再実行しない。

最終報告は「点検件数／変更した内容または改善案／検証結果／判断が必要な項目」。秘密・全文プロンプト・生のコマンド引数は含めない。gatewayが送信するので、点検エージェントが別途Slack等へ投稿しない。
