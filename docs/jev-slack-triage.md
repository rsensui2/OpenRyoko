# Jev による Slack トリアージと会話追跡

Slack の受信メッセージを TypeSafe Jev の Choice / Noul API で分類し、コードで `reply` / `react` / `silent` を決定する。`reply` は通常のセッションへ渡す意味であり、外部操作の承認ではない。回答本文や実作業を生成する既存のセッションエンジンは継続して使う。

## 設定

ダッシュボードの設定 → Slack → 空気読み判定から方式を選ぶ。ルートの Slack 接続と、追加した各 Slack 接続の両方で設定できる。

| 方式 | 設定 | 曖昧・障害時 |
|---|---|---|
| 従来の CLI | `backend: cli` | 従来の処理 |
| Jev のみ | `backend: jev`, `jev.fallback: none` | CLI は起動せず、明示宛先や会話継続の規則で判断 |
| Jev + CLI | `backend: jev`, `jev.fallback: cli` | 従来 CLI へ引き継ぐ |
| 比較運転 | `backend: jev-shadow` | CLI の結果を使い、Jev は並行して観測 |

`backend: jev` のフォールバック既定値は `none`。未設定の既存環境は `cli` を維持する。画面で方式を変えた後は全体の「設定を保存」を押す。

同じ画面で API キーを保存・削除し、合成文を使って接続を確認できる。キーは `JINN_HOME/credentials/typesafe.json`（所有者のみ読み書き可）に保存し、画面・設定取得 API・ログへ返さない。入力欄は保存後に空に戻る。キーの変更は次の判定から有効になる。

代わりに gateway のプロセス環境へ `TYPESAFE_API_KEY` を渡してもよい。標準名の場合は保存済みキーを優先する。独自の `apiKeyEnv` を指定した場合はその環境変数だけを使う。Mac のシェルと launchd、Docker のプロセス環境は別なので、利用する起動経路ごとに設定する。Docker Compose では private な `env_file` を指定し、コンテナを再作成する。キーを config.yaml、ソース、イメージへ書かない。

```yaml
connectors:
  slack:
    triage:
      enabled: true
      backend: jev  # cli（既定） / jev-shadow / jev
      engine: claude
      model: claude-haiku-4-5
      timeoutMs: 45000
      threadContextLimit: 10
      conversationIdleTimeoutMs: 1800000
      conversationMaxEntries: 5000
      jev:
        fallback: none
        useCapabilities: true  # スキル・担当領域を考慮（既定）
        model: jev-1.13.0
        apiKeyEnv: TYPESAFE_API_KEY
        timeoutMs: 3000
        maxConcurrent: 4
        minProbability:
          reply: 0.8
          react: 0.9
          silent: 0.97
```

DM、明示メンション、継続中の1対1会話は既存の直接ルートを使う。純粋な感謝はリアクション判定に回す。Jev は宛先・意図・会話との関係・軽い反応の種類を4つの Choice、回答や作業が求められるかを Noul で並列に評価する。独立した質問の確率を掛け合わせない。意図のうち依頼・続行・訂正・停止・複合依頼は同じ Choice の排他的な選択肢なので、応答の要否にはその合計確率を使う。API の小数丸めを許容するが、閾値を超えるように確率を再調整しない。

短い名前呼びや、その場で返事を試す「Ryokoの空気読みテスト」のような投稿も応答対象に含める。名前を話題にしただけの発言、将来のテスト予定、結果報告、引用、人への依頼とは文脈で区別する。宛先が「bot単独」か「botを含む部屋全体」かで割れる場合は、その同じ Choice の確率を合算できる。ただし追加で「このbotの返事が必要」の Noul と、依頼等の意図がそれぞれ返信閾値を満たすことを要求する。人間・不明の宛先や他botへの続行には、この経路を適用しない。特定の名前をコードで強制一致させない。自己名は本体と同じ `resolveAssistantName` で、接続先社員の `displayName` → 社員の `name` → `portal.portalName` → 既定名 `Ryoko` の順に解決する。社員の設定変更は次の投稿から判定と自己履歴の表示名へ反映する。Slack上の自己投稿・@メンションの識別は引き続きbotユーザーIDを使う。解決済みの実名は宛先等の質問にも明示し、スキル説明や他人の発言に登場する別名を自分の別名と解釈しないようにする。

### 自分の能力で役に立てるか

設定画面の「スキル・担当領域を考慮」（`jev.useCapabilities`、既定で有効）では、さらに独立した Choice で、いま未解決の依頼に具体的に貢献できるかを判定する。能力が合うだけで人宛てや宛先不明の発言・雑談へ割り込むことはない。

全体に開かれた依頼では、botを含む宛先・依頼の意図・具体的な貢献可能性が、それぞれ返信閾値を満たすことを要求する。「このbotの返事が期待されるか」が強い否定なら採用しない。名指しされていないため応答期待が不確かでも、全体への依頼と能力の適合が明確なら応答対象になる。bot単独と全体の宛先確率が割れる場合も同じ条件を使う。一方、明確な本人への依頼や既存作業の継続は、能力一覧に該当項目がなくても本体へ渡す。できないことの説明や停止も応答の一部だからである。

入力は担当社員本人の `persona` / `provides` と、そのインスタンスにインストールされたスキルのfrontmatterの名前・説明だけ。トリアージの `persona` を設定した場合は役割説明として優先する。スキル本文・MEMORY・MCPの認証設定は読み込まない。宣言された能力は、認証完了や外部操作の承認を意味しない。

スキル一覧は30秒キャッシュし、変更通知でも破棄する。最大128候補からメッセージとの軽い文字列一致で24件を選び、役割・サービスを含めて記述6000文字以内に制限する。これは前処理であり、能力の意味判定はJevが行う。省略があれば `truncated` を伝え、一覧にないことを「できない」の証拠にはしない。設定をオフにすると能力メタデータと追加質問の両方を送らず、従来の5質問で判定する。能力の判定ラベル・確率だけを診断ログに残し、役割・スキル説明はログに残さない。

Jev 専用モードでは、判定の不一致、確率不足、履歴の欠落、タイムアウト、キー未設定などでも CLI を起動しない。明示された宛先、DM、完全な履歴に裏づけられた続行は保護し、不明な部屋の会話には沈黙する。このため不確かな暗黙の依頼を取り逃すことはある。確率は正解率の保証ではなく、実測の正解率と分けて評価する。

`jev-shadow` は従来の判定と並行して分類結果だけを観測する。Jev の完了を待って従来判定を遅らせない。新しい Jev ログにはモデル、所要時間、選択肢、確率、トークン数、固定の失敗理由だけを記録する。APIキーと会話本文は含めない。

分類先は公式の `https://api.typesafe.ai/v1/systemone` に固定し、リダイレクトを認めない。判定対象本文は最大4,000文字、直近10発言は各400文字まで。取得履歴の欠落は明示する。キーと同様、会話本文も評価結果ファイルへ保存しない。

## リアクション

- 軽い感謝・挨拶・祝いは、判定後すぐ絵文字で返し、回答エンジンを起動しない。
- 回答や作業を進める場合は、セッションへ渡す前に `eyes`（👀）を付ける。沈黙する場合は付けない。
- 人が付けた絵文字リアクションも、対象となった正確な投稿を取得して判定する。返信する場合は元のスレッドと同じセッションへ渡す。
- 自分の確認質問への承認と、完了報告へのお礼を区別する。絵文字を付けただけで会話を継続中にしたり、完了済みの作業を自動再開したりしない。
- 入力待ちを根拠に続行を強制する場合は、待っている相手本人と最後の質問投稿の両方を照合する。別人や古い投稿への反応を、現在の承認として読み替えない。キューで取り消された依頼の処理中マークも除去する。

## 会話追跡

- 実際に送信できた文章を会話への参加として記録する。リアクションや処理中の `eyes` だけでは、次の発話を無条件で拾わない。
- 通常の1対1会話は既定30分で直接ルートの対象から外れ、再びトリアージを通す。別の人が同じスレッドへ参加しても無条件の1対1扱いを外す。
- スレッドに返信した事実と、いま直接応答すべき状態を別々に持つ。会話が終了しても、参加済みスレッドの後日の発言はメンション限定設定の入口を通り、トリアージで判断できる。
- 構造化された Codex のゴール評価が `waitingFor: user`（人への情報・判断・承認の依頼）を示し、対応する最終文章を送信できた場合は `awaiting_input`、完了／取消なら `completed` を記録する。ジョブ完了待ちや一般的な障害は入力待ちにしない。過去のゴール、エラー、中断、送信失敗からは状態を推測しない。
- トップレベルで始めた依頼と、その返信スレッドの対応を保持する。スレッド内で回答や完了が生じたら元の入力待ちにも反映し、同じ人の別件の入力待ちは消さない。
- Claude ネイティブのゴールや通常の自由文には確実な状態通知がないため、その場合は直近の履歴と有効期間で判断する。疑問符だけで「入力待ち」と断定しない。
- 件数上限を持つ。状態はインスタンスの `state/slack-conversations-*.json` に、本文を含めず所有者のみ読み書きできる権限で保存する。起動時に復元し、通常会話の有効期間も維持する。保存できない場合もメモリ上で継続する。強制終了では最大100msの未保存更新が失われうる。

Slack の長いスレッドは最大4ページまで取得し、現イベントより前の最新10件を渡す。取得が途中なら不足フラグを立て、古い発話から続行を強制しない。Ryoko自身と他botを区別する。

## 検証と切り戻し

単体テストでは通信をモックし、キーなし、遅延、巨大応答、不正な分布、同時実行上限、他bot、返信失敗、感謝の後の新規依頼、入力待ちの保持、Jev 専用での CLI 未起動、👀と即時リアクションなどを確認する。API キーの認証・保存権限・応答への非露出と、設定画面の操作も検証する。実APIの評価は合成文でも実施でき、実Slackへテスト投稿する必要はない。

実会話を評価に使う際は利用者の許可を得て、宛先サービスを明確にし、識別子・メール・URL・秘密を除去する。開発用と未使用の検証用をスレッド単位で分け、明示メンション等の規則だけで決まる結果と、意味分類が必要な結果を分けて報告する。API の採用率だけでなく、最終的な見逃し・不要な応答・適切なリアクションを測る。

判定を従来へ戻すときは `triage.backend: cli` に変更する。新しい会話追跡は継続する。コード全体の切り戻しは、保存済みの以前のパッケージとコンテナイメージを使う。
